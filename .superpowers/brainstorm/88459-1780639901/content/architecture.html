System Architecture — Social Platform Integration

How all pieces connect. Review each layer and confirm before we move to the design doc.

Data Flow Overview
── WRITE PATH (behavioral events) ──────────────────────────
Flutter App → HTTP POST events → leo-cdp-framework ingestion API → ArangoDB
                                                             ↓ CDC poller
                                                             LEO Activation → Kafka → Scoring → PG

── READ PATH (recommendations & scores) ────────────────────
Social Backend ← REST API ← LEO Activation (interest scores, trending tickers, NBA)

── IDENTITY PATH ───────────────────────────────────────────
Social Backend → phone/email → GET /identity/resolve → profile_id → Social Backend
What changes in LEO Activation

1. New Social Event Types

CDC scoring consumer learns to weight new event types from ArangoDB:

  • social_post — user posts about a ticker
  • ticker_reaction — like/bullish/bearish on a post
  • discussion_comment — comments in ticker thread
  • ticker_follow — follows a ticker's discussion

2. Identity Resolution Endpoint

New endpoint in api/ for federated lookup:

GET /identity/resolve
  ?email=x@y.com
  | ?phone=+84...
→ { profile_id, tenant_id }

3. Trending Tickers API

New read endpoint aggregating social activity signals into ticker rankings — feeds the social feed's "Hot Discussions" section.

GET /social/trending-tickers
→ [{ ticker, post_count, reaction_count, score }]

4. Existing APIs (reuse as-is)

Social platform calls these unchanged:

  • GET /recommendation/interested/{ticker}
  • GET /recommendation/profile_affinity/{id}
  • GET /recommendation/nba/{id}
What the social platform owns (not in LEO)
Flutter App: UI, feed rendering, discussion threads, posting
Social Backend: Post/comment/reaction storage, follow graph, feed ranking, push notifications
Social DB: Posts, comments, reactions, follows (separate from LEO's PG)
