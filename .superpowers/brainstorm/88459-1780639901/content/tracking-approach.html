Where to capture behavioral events?

Backend via RabbitMQ vs. Flutter frontend tracking — or both

A

Backend via RabbitMQ consumer Recommended

Add a RabbitMQ consumer that listens to the existing mutations queue and forwards events to leo-cdp-framework's ingestion API. Zero changes to Flutter. All mutation events (post, like, react, comment, share, bookmark, follow) are already guaranteed to flow through here.

Flutter → Social Backend → RabbitMQ
                                  ↓ new consumer
                             leo-cdp-framework ingestion API
                                              ↓
                                    ArangoDB → LEO Activation

Pros

  • 100% reliable — events never missed, no offline risk
  • Structured & validated data (passed backend logic)
  • Zero Flutter changes
  • Single place to maintain event mapping
  • Reuses existing infra you already have

Cons

  • Misses passive signals (scroll, view time, tap patterns)
  • Slight async delay (usually fine for scoring)
B

Flutter frontend tracking

Flutter app calls leo-cdp-framework's HTTP ingestion API directly for every user interaction — including passive ones (ticker page views, scroll depth, time-on-discussion).

Flutter → HTTP events → leo-cdp-framework
Flutter → mutation → Social Backend (separately)

Pros

  • Captures passive engagement (views, scroll, time)
  • Richer signal for interest scoring
  • How leo-cdp-framework was originally designed

Cons

  • Events lost when offline or app killed
  • Duplication risk for mutations (front + back both track)
  • Flutter tracking SDK maintenance burden
  • Harder to ensure data quality
C

Hybrid — backend for mutations, Flutter for passive

RabbitMQ consumer handles all writes (post, like, react, comment, share, bookmark, follow). Flutter only tracks passive signals that never hit the backend: ticker page view duration, scroll depth in discussion threads, feed impression events.

RabbitMQ consumer → mutations → leo-cdp-framework
Flutter                  → views/scroll → leo-cdp-framework

Pros

  • Reliable mutations + rich passive signals
  • No duplication — clear ownership per event type
  • Best data quality for scoring

Cons

  • Two tracking surfaces to maintain
  • More complex to implement upfront
