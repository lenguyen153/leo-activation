Integration Approaches

How the social platform connects to LEO Activation — pick the architecture that fits

A

LEO as Data Provider + Event Gateway Recommended

LEO exposes a clean read API for the social platform and adds a new /social/events ingestion endpoint. Social behavioral events (posts, reactions, trending tickers) are pushed into LEO's existing Kafka/CDC scoring pipeline. Identity resolved via a new /identity/resolve endpoint (phone/email → profile_id).

Pros

  • Minimal changes to LEO core
  • Social platform only needs HTTP — no Kafka knowledge
  • New routes are isolated in api/
  • Fits the existing REST pattern

Cons

  • LEO becomes a dependency — social platform blocked if LEO is down
  • High-volume social events may need rate limiting
Social Platform → POST /social/events → LEO → Kafka → Scoring Consumer
Social Platform ← GET /recommendation/interested/{ticker} ← LEO
Social Platform ← GET /identity/resolve?email=… ← LEO
B

Shared Kafka Bus (Event-Driven)

Both systems share a Kafka cluster. Social platform publishes to a social-events topic. LEO's scoring consumer is extended to also consume that topic. LEO publishes interest score updates to a topic the social platform subscribes to. Fully decoupled at runtime.

Pros

  • Fully decoupled — neither blocks the other
  • Natural fit for high-volume event streams
  • Resilient — events buffer if one side is down

Cons

  • Social platform team must learn Kafka
  • More infra to manage (topic ACLs, schemas)
  • Harder to debug event flow across systems
Social Platform → Kafka: social-events → LEO scoring consumer
Social Platform ← Kafka: interest-scores ← LEO NBA publisher
C

Integration Gateway / BFF Layer

A thin Backend-for-Frontend service sits between the social platform and LEO. It handles identity resolution, data aggregation (merging LEO scores + social graph), event routing, and caching. Both systems stay completely unaware of each other's internals.

Pros

  • Cleanest boundary — neither product changes for the other
  • Can version and evolve the integration independently
  • Best for long-term multi-product growth

Cons

  • Extra service to build, deploy, and maintain
  • Overkill for two products sharing a team
  • Adds latency and a new failure point
Social Platform ↔ Integration Gateway ↔ LEO Activation
Gateway handles: identity, event routing, score aggregation
